> S1 的后端、前端、真实模型和页面联调验收已通过。S2—S6 尚未开始。各阶段以本清单和 `docs/evidence/` 中的实际记录为准。

## 1. 如何执行

每个阶段都包含三个可记录的检查点：

1. **B 后端局部验收：**用服务测试、固定模型响应和 HTTP 请求测试当前功能，不必等待页面完成。
2. **F 前端局部验收：**使用固定 API 响应验证渲染、交互和页面状态，不必等待后端完成。
3. **I 阶段联调验收：**接通真实后端，完成该阶段用户流程；新增 AI 能力还需实际调用模型。

B/F 的开发顺序可以调整，I 必须在两者完成后进行。局部通过后即可提交对应的真实变更；只有 I 通过才能将该阶段记为完成。Milestone 内所有阶段通过后，再登记其实际 Commit 区间。

每项填写：状态、测试编号、实际结果、证据路径、SHA。状态包括未开始、开发中、通过、未通过。固定响应通过不代表模型效果通过。

- [ ] 在调用模型前校验空白、2,000 字符边界和请求体。

**后端通过标准：**空白/2,001 字符返回 400；合法空结果返回 200；服务不可用、无配置、超时返回各自错误，不能伪装为空结果。

## S4

**目标：无效模型输出能获得一次修复机会，最终失败后用户能继续操作。**  
依赖：S3。

### 后端：有界修复

- [ ] 结构或引用无效时最多修复一次；正常结果只调用一次。
- [ ] 框架/SDK 重试计入总预算，不叠加隐藏调用。
- [ ] 替身序列按每个业务请求重置，记录次数用于测试。
- [ ] 超时或服务不可用不触发格式修复。
- [ ] 执行 S4-B01—B04，通过替身计数/服务测试确认次数。

**后端通过标准：**非法→合法返回 200，恰好 2 次；非法→非法返回 502，恰好 2 次；正常/超时/不可用按约定结束，均不额外调用。

通过后可提交：`feat(ai): 增加有界输出修复和调用次数控制`。

### 前端：故障恢复

- [ ] 服务内部修复期间维持处理中，不另发浏览器业务请求。
- [ ] 最终失败时恢复按钮、保留原文；成功后清理旧错误。
- [ ] 执行 S4-F01/F02：延迟成功、失败后用户重试成功。

**前端通过标准：**页面不重复请求、不累积旧卡片，最终状态与最后一次操作一致。

通过后可提交：`feat(web): 支持审查故障后的恢复操作`。

### 联调与出口

- [ ] 执行 S4-I01，同时核对浏览器请求数与后端模型调用数。
- [ ] 回归 S3 的永远错误引用：最终仍是 502；内部最多调用次数由 1 增为 2。

**阶段通过：S4 的 B/F/I 用例通过，相关旧能力正常。S3/S4 均通过可验收 M2。**
