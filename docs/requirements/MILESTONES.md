## 2. Commit 区间如何记录

1. 每个 Milestone 使用业务目标连续的实际 Commit 区间。
2. 本模板将起止 SHA 定义为“均包含”；在平台确认其界面语义后选择对应提交。
3. M2 的起始提交是 M1 结束之后的第一条实际提交；M3 同理，避免重复覆盖或无故漏掉提交。
4. 单人第一版可以沿一条清晰主线开发。若存在分支合并，要核对平台实际展示的提交及可达历史。
5. 文档完善、测试补充和真实修复应计入关联阶段，不应从历史中隐藏。

全部文件提交完成后，再读取最终 HEAD 填写到平台或仓库外的提交材料。仓库内末阶段结束 SHA 可以注明“上传前读取最终 HEAD”，不必为了把某次提交的 SHA 写入该提交自身而反复修改。平台的末阶段应覆盖上传版本中的最终文档提交。

查看实际历史：

```sh
git log --reverse --format='%h %s'
git rev-parse HEAD
```

检查第二阶段的提交列表时可使用：

```sh
git log --reverse --format='%h %s' <M1结束SHA>..<M2结束SHA>
```

Git 的 `A..B` 排除 A 并包含 B；不要因此把平台的“起始 Commit”误填成上个阶段的结束提交。以上命令中的 SHA 都必须来自真实仓库。

## 6. 简短的阶段验收记录格式

每个阶段结束时填写一份，放在项目 docs/ 中或本文件内：

```text
阶段：
检查点：后端 B / 前端 F / 联调 I
测试用例 ID：
模式：固定模型 / 固定 API / 真实前后端+固定模型 / 真实模型
验收日期：
目标分支：
验收时 HEAD：
实际实现：
主要涉及文件：
执行的命令/手动操作：
实际结果：
结论：未执行 / 通过 / 未通过
模型和 Prompt 版本（如涉及）：
未完成事项或已知限制：
证据文件：
```

截图和报告是补充材料；代码、提交与可复现的验证步骤仍是主要依据。不要将计划描述直接作为测试通过的证明。

后端局部测试通过时提交对应代码和测试；前端固定响应测试通过时提交页面及样例；联调修复形成实际变更时再提交修复。不要等项目全部完成后再拆历史，也不要为了凑 B/F/I 三种提交强行增加空提交。

## 7. 下一步 TODO：平台填写候选

以下工作建立在本 PRD 的模块设计上。提交时将路径替换为最终仓库的实际位置，删除已经完成的条目，并保持至少 5 条。

1. **需求版本对比。**在 RequirementParser 和 ReviewService 中引入需求版本关系；比较修改前后的原文，标记新增、仍待处理和已解决的问题。验收：修改优惠券时间规则后，旧时间口径问题的状态能准确更新。
2. **多轮澄清。**扩展 ReviewSessionStore 与 AcceptanceService，保留每轮确认记录；后续轮次只询问仍未明确的事项。验收：已确认的自然日口径不会在第二轮丢失或再次变成未确认。
3. **用例分类。**为验收 DTO 和页面增加正常、异常、边界类别，并允许用户调整。验收：跨自然日和重复领取用例能够分类、修改并正确导出。
4. **JUnit 草稿导出。**扩展 ReportExporter，将确认后的用例转换为带来源说明、待实现断言的 Java 测试骨架。验收：生成文件语法有效，业务断言标记为待开发而非伪装成已通过测试。
5. **Prompt 版本评测对比。**扩展评测工具，对相同 E01—E08 输入运行两个 Prompt 版本，记录目标问题覆盖、误报和验收规则错误。验收：能从实际结果生成可追溯的对比表。
6. **模型调用统计。**在 AiGateway 记录耗时、调用次数、可获得的 token 用量与错误类别。验收：修复重试计入同次操作；供应商未返回用量时显示不可用，不填估算值冒充实测。
